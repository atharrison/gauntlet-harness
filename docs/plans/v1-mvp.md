# Gauntlet Harness — v1 MVP Plan

> **Status:** Planning · **Author:** Andrew Harrison · **Last updated:** 2026-08-15
> **Linear:** Project = [Review Harness V1 MVP](https://linear.app/atharrison/project/review-harness-v1-mvp-2ce2b8648107) · Team = Team Andrew (`ATH`) · Note: hackathon tickets FIR-1–FIR-11 are now `ATH-1`–`ATH-11` after the team key rename.  
> **Goal:** Take the hackathon winner to a production-ready self-hosted tool that Ribbiot can deploy and use for daily PR reviews.

---

## Context

The hackathon deliverable (June 2026) proved the core pipeline works: paste a PR URL, agents produce structured findings, a human curates and submits a review comment. The v1 MVP picks up from that foundation and adds the infrastructure, UX, and data layer needed to use it every day at work.

**Key constraints:**

- MIT-licensed open source; Andrew is the sole maintainer working on personal time
- Ribbiot will consume it as a third-party OSS tool (not proprietary)
- Deployed as a shared Railway instance for the Ribbiot eng team
- Target: usable within 2–3 weekends (~September 2026)

---

## Goals

1. **Authentication** — GitHub OAuth so any Ribbiot teammate can sign in without a shared password
2. **PR Review Queue** — a page that surfaces open PRs from configured repos, tracks their review lifecycle, and supports re-review
3. **Durable review state** — replace the in-process `Map` cache with Supabase-backed storage so reviews survive restarts and can scale
4. **Memory recall** — wire `search_past_reviews` into the context agent so past review summaries inform new reviews
5. **Three new domain agents** — Conventions, Performance, and Style round out the full review suite
6. **Self-hosting guide** — polished README + step-by-step setup so any developer can deploy from scratch
7. **Bug fixes** — fix `finding_count = 0` persistence bug and other known data integrity issues

## Non-Goals (v1)

- Inline line-level PR comments (post PR-level summary comment only; inline is post-MVP)
- Vector/semantic search over review history (pgvector-based code index deferred)
- Per-user review settings or preferences
- SaaS multi-tenancy (single org instance only)
- CLI polish (the `npm run review` script points at a non-existent file — leave for later)

## Architecture Changes

### 1. Supabase-backed Review State (replaces `review-cache.ts`)

The current `review-cache.ts` is an in-process `Map` with a 1-hour TTL. It works on a single Railway instance but breaks with replicas or restarts mid-review. Replace it with a `reviews` table in Supabase.

**New table: `reviews`**

```sql
create table reviews (
  id text primary key, -- UUID, generated by start route
  pr_url text not null,
  pr_metadata jsonb, -- { owner, repo, number, title, head, base, author }
  mode text not null default 'full', -- 'full' | 'quick'
  status text not null default 'RUNNING', -- RUNNING | COMPLETE | ERROR
  result jsonb, -- serialized PRReview (set on done)
  submission jsonb, -- serialized ReviewSubmission (set on finalize)
  finding_count int generated always as (jsonb_array_length (result - > 'findings')) stored,
  error_message text,
  created_at timestamptz default now (),
  updated_at timestamptz default now ()
);
```

The SSE route writes `status=RUNNING` on start and `status=COMPLETE` + `result` on done. The finalize route reads from this table instead of the in-process map, then writes `submission`. The `finding_count` generated column fixes the `= 0` persistence bug — no code change required to fix the count.

### 2. PR Queue

**New table: `tracked_prs`**

```sql
create table tracked_prs (
  id uuid primary key default gen_random_uuid (),
  owner text not null,
  repo text not null,
  pr_number int not null,
  pr_url text not null,
  pr_title text,
  pr_author text,
  pr_opened_at timestamptz,
  pr_closed_at timestamptz,
  status text not null default 'OPEN', -- OPEN | IN_REVIEW | REVIEWED | CLOSED
  last_review_id text references reviews (id),
  review_count int not null default 0,
  source text not null default 'MANUAL', -- MANUAL | WEBHOOK
  created_at timestamptz default now (),
  updated_at timestamptz default now (),
  unique (owner, repo, pr_number)
);
```

**New table: `configured_repos`**

```sql
create table configured_repos (
  id uuid primary key default gen_random_uuid (),
  owner text not null,
  name text not null,
  webhook_secret text, -- set when webhook is installed; null = no webhook
  active boolean not null default true,
  created_at timestamptz default now (),
  unique (owner, name)
);
```

### 3. GitHub OAuth

Use `@supabase/ssr` + Supabase Auth with the GitHub OAuth provider. Supabase handles token exchange and session cookies; Next.js middleware validates the session on every request. The `ACCESS_PASSWORDS` env var remains as a fallback for non-authenticated deployments.

The GitHub access token from the OAuth session doubles as the Octokit token — users authenticate once and the tool can read their repos and post comments on their behalf.

**Auth flow:**

1. Unauthenticated request → redirect to `/login`
2. `/login` → "Sign in with GitHub" button → Supabase OAuth callback
3. Callback → session cookie → redirect to queue page
4. Middleware validates session on every route

### 4. GitHub Webhook

A new API route `POST /api/webhooks/github` receives GitHub webhook events. On `pull_request` events with `action: opened | reopened | synchronize`, it upserts a `tracked_prs` row with `source=WEBHOOK`.

Each `configured_repo` can have a `webhook_secret` for HMAC signature validation. The self-hosting guide will walk through GitHub webhook setup.

### 5. Memory Recall (wiring `search_past_reviews`)

`search_past_reviews` already exists as a tool in `src/tools/memory.ts` but is never called by the context agent in practice. The fix: add a system-level instruction to the context agent's prompt telling it to call `search_past_reviews` early in the loop to retrieve relevant past review context before diving into the diff.

No schema change needed — `review_history` already stores review summaries. The `storeReview` function is already called on finalize.

### 6. New Domain Agents

Following the same pattern as Correctness and Security (single-shot, structured output via `DomainResultSchema`):

- **Conventions agent** — enforces team coding patterns: naming conventions, import ordering, enum usage, shared utilities vs duplication, docstrings/type hints. Feed it a short team conventions doc as part of the system prompt (loaded from a `CONVENTIONS_FILE` env var path, optional).
- **Performance agent** — flags N+1 query patterns, inefficient loops, unnecessary allocations, missing pagination, blocking I/O in async contexts.
- **Style agent** — readability, clarity, dead code, overly complex expressions, missing/stale comments.

All three join the `Promise.all` fan-out in `coordinator.ts`. The coordinator's merge step already handles arbitrary domain result arrays — no coordinator logic changes needed.

## Database Migration Plan

All changes land in a single new migration file to keep the apply-order simple:

```
supabase/migrations/20260815_reviews_queue.sql
```

Includes:

1. `reviews` table (with `finding_count` generated column)
2. `tracked_prs` table
3. `configured_repos` table
4. `settings` table (key/value store for in-app configuration like team conventions)
5. `updated_at` trigger for all tables
6. RLS policies: authenticated read-all, insert/update own rows; settings writable by any authenticated user
7. Index on `tracked_prs(status)`, `tracked_prs(owner, repo)`

Existing tables (`memories`, `review_history`, `review_checkpoints`) are untouched. The `review_history` table continues to be used by `storeReview` + `search_past_reviews`.

## Post-MVP (v2 Candidates)

These are intentionally out of scope for v1 but worth capturing:

- **Inline PR comments** — post line-level `pulls.createReviewComment` not just `issues.createComment`
- **Vector/semantic code search** — pgvector index over review history and codebase for deeper context
- **CLI polish** — wire `src/cli/index.ts` so `npm run review` works from the terminal
- **Supabase checkpoint adapter** — persist agent checkpoints to Supabase (not just in-memory)
- **Team pattern memories** — aggregate recurring findings into named team-level memories injected into every review
- **Review assignment** — assign a PR review to a specific teammate via the queue
- **Slack/email notifications** — notify when a webhook-triggered PR needs review
- **Multi-org support** — manage multiple GitHub orgs/Supabase projects from one deployment

## Resolved Decisions

1. **OAuth scope**: Use full `repo` scope — grants read/write to all user repos, acceptable for an internal trusted tool. Users sign in via GitHub OAuth and are immediately ready to use the tool. An admin separately configures which orgs/repos are available for review via the settings page. No separate PAT setup required.

2. **Webhooks vs GitHub App**: Use **individual repo webhooks** for MVP. Simpler, matches the `configured_repos` model (admin registers repos in settings, and setting up a webhook is part of that flow). Documenting the limitation: with repo webhooks, each repo in the `configured_repos` list needs its webhook manually registered. A GitHub App (org-level install) would auto-cover all repos in an org without per-repo setup, but requires creating and publishing a GitHub App — deferred to v2.

3. **Conventions file**: In-app text editor in the settings page, stored in Supabase. No file path env var, no external URL. Admin edits conventions in the UI; the Conventions agent loads it from the database at review time.

4. **Re-review badge**: When a `synchronize` event flips a `REVIEWED` PR back to `OPEN`, the queue should show a "⟳ Updated" badge so the team knows the PR changed since its last review. Low-effort UI indicator.
